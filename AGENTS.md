# Agent Context: AI Gateway Demo

## Project Overview

Single Cloudflare Worker that serves a web UI for demonstrating AI Gateway features:

- **Custom Costs**: Override per-token pricing via `cf-aig-custom-cost` header
- **Spend Limits**: Gateway-level budget enforcement that returns 429 when exceeded
- **Rate Limiting**: Request-based limits (fixed/sliding window) via gateway config
- **Caching**: Per-request cache TTL and custom cache keys via `cf-aig-cache-ttl`
- **Custom Metadata**: Tag requests with `cf-aig-metadata` for log filtering
- **Identity-Aware Gateway**: Cloudflare Access + custom domain auto-injects `cf.user_id`
- **Guardrails**: Toggle Llama Guard content moderation on/off at the gateway level — also the dominant latency factor in this demo (see Important Implementation Details)
- **Workers AI**: All traffic routes to Cloudflare Workers AI models via the REST API

## Architecture

```
Two demo modes, one Worker:

1. Human identity (browser → gateway directly):
   Browser → ai-gw.jsherron.com/demo (Worker serves UI)
          → ai-gw.jsherron.com/compat/chat/completions (direct, Access injects cf.user_id)
          → ai-gw.jsherron.com/demo/api/* (Worker handles management with service token)

2. Service identity (Worker proxies everything):
   Client → workers.dev URL /api/chat → AI Gateway (custom domain with service token) → Workers AI
                                        → cf.common_name in logs (NOT cf.user_id)
```

- **Gateway mode URL**: `https://ai-gw.jsherron.com/demo` — behind Access, human identity
- **Worker proxy URL**: `https://ai-gateway-demo-worker.jsherron-test-account.workers.dev` — no Access, service token
- **Worker routes**: `ai-gw.jsherron.com/demo` and `ai-gw.jsherron.com/demo/*` (zone: jsherron.com)
- **Gateway direct**: `ai-gw.jsherron.com/compat/chat/completions` goes directly to AI Gateway (no Worker route)
- **Management calls** (stats, settings) use the gateway **ID** via Cloudflare REST API
- **KV** stores `custom_costs` and `gateway_settings`

### Identity in Logs

| Auth method          | Identity field   | Dashboard visibility                               | User agent          |
| -------------------- | ---------------- | -------------------------------------------------- | ------------------- |
| Human (Access + IdP) | `cf.user_id`     | Shows in dashboard, User Insights, per-user limits | Browser             |
| Service token        | `cf.common_name` | Logs API only — does NOT appear in dashboard UI    | `cloudflare-worker` |

**Service tokens do not show as identities in the AI Gateway dashboard.** The `cf.common_name` field is visible in the logs API response but is not surfaced in the dashboard's User Insights or per-user analytics views. Only human identity (`cf.user_id` from IdP authentication) appears in the dashboard. This is the key value-add of Identity-Aware Gateway with human auth.

## Security

### Admin gate (`requireAdmin`, `src/auth.ts`)

`dualRoute()` mounts every handler at both `/demo/api/*` (behind the Access app that protects the custom domain) and `/api/*` (the public `*.workers.dev` URL — `workers_dev = true`, no Access there). Until 2026-10-28 this meant `/api/settings`, `/api/costs` (write), and `/api/stats` were reachable by literally anyone on the internet, with zero auth, able to disable the gateway's own spend/rate limits or read live cost/usage data. Found and fixed in the same session as the `fix/security-hardening` branch evaluation below.

**Gated** (`requireAdmin()`, both `/api/*` and `/demo/api/*`): `/bootstrap`, `/settings`, `/guardrails`, `/costs` (POST), `/stats`.
**Intentionally open, both mount points, no auth** — this is the documented "service identity" demo: `/chat` (POST), `/costs` (GET — just your own saved per-token rates, not secret).

`requireAdmin()` passes if **either**:

1. `Authorization: Bearer {CLOUDFLARE_API_TOKEN}` — compared with `timingSafeEqual()` (hash both values to a fixed size, then constant-time byte compare — see `src/auth.ts`). Covers scripts, CI, the bootstrap flow.
2. A **cryptographically verified** `Cf-Access-Jwt-Assertion` header — `jose`'s `jwtVerify` + `createRemoteJWKSet` against `CF_ACCESS_TEAM_DOMAIN`'s JWKS, checking `issuer` and `audience` (`CF_ACCESS_AUD`). Covers human logins and service tokens authenticated through the Access app.

**Why not `path.startsWith("/demo")`, or a `Host` header check?** Both are bypassable. `workers_dev = true` serves `/demo/*` on the unprotected `*.workers.dev` host too (confirmed live: `curl https://<worker>.workers.dev/demo/api/stats` returns real data with zero auth), and a client can send any `Host` header it wants over plain HTTP — Cloudflare's edge doesn't correct a mismatched one before your Worker sees it. Only a validly-signed JWT proves Access, because forging one needs Cloudflare's private signing key.

If `CF_ACCESS_TEAM_DOMAIN`/`CF_ACCESS_AUD` aren't set, the Access-JWT path always fails closed — admin endpoints then only accept the bearer token, same as before this fix existed.

### CSRF

`app.use("*", csrf())` (Hono's built-in middleware). Low actual exposure here: every mutating endpoint requires `Content-Type: application/json` and a real JSON body, and this app sends no CORS headers — so a cross-site browser `fetch()` with JSON either never completes (blocked by the CORS preflight the server won't satisfy) or, for the simple-request content-types `csrf()` actually polices (form-urlencoded/multipart/text-plain), fails JSON parsing server-side anyway. Kept as cheap defense-in-depth for if a form-style endpoint is ever added.

### Input validation (`chatHandler`)

`model` required non-empty; `prompt` non-empty, capped at 4000 chars; `cache.key` capped at 512 chars and rejected if it contains control characters (CR/LF) — the Fetch API's `Headers` already rejects raw CRLF in header values, but validating here turns that into a clean 400 instead of an uncaught throw → 500; metadata string values capped at 200 chars (`validateMetadata`, pre-existing — see below).

### Known-accepted residual: dev-tooling `npm audit` findings

6 high-severity findings remain, all transitive through `@cloudflare/vitest-pool-workers` → `miniflare` → `sharp`/`undici`/`zod`. These simulate the Workers runtime locally for `wrangler dev`/vitest; **none of this ships in the deployed Worker bundle**. npm's only offered fix is `--force`, which downgrades `vitest-pool-workers` to 0.12.21 (older than the 0.23.0 we're on) and risks breaking the test suite for no production-facing benefit. Re-run `npm audit` periodically — Cloudflare may ship a patched `miniflare` release that resolves this forward instead of backward.

## Important Implementation Details

### Custom Costs Header

```
cf-aig-custom-cost: {"per_token_in":0.000001,"per_token_out":0.000002}
```

- Sent on every `/api/chat` request if enabled
- Values stored in KV, editable in web UI
- AI Gateway uses these instead of public pricing for cost tracking

### Caching Headers

```
cf-aig-cache-ttl: 300
cf-aig-cache-key: my-key      (optional)
cf-aig-skip-cache: true       (optional, bypasses cache)
```

- Per-request override of gateway cache settings
- Cache status returned in response header `cf-aig-cache-status` (HIT / MISS)

### Custom Metadata Header

```
cf-aig-metadata: {"team":"AI","user":12345}
```

- Up to 5 key-value pairs (string, number, or boolean)
- Appears in AI Gateway logs for filtering and analytics
- **Reserved:** Keys starting with `cf.` are reserved. When Identity-Aware Gateway is configured with Cloudflare Access, `cf.user_id` is automatically injected into metadata.

### Workers AI via Custom Domain

```
POST https://ai-gw.jsherron.com/compat/chat/completions
Headers:
  Authorization: Bearer {CLOUDFLARE_API_TOKEN}
  CF-Access-Client-Id: {service_token_id}    (for Worker/service auth)
  CF-Access-Client-Secret: {service_token_secret}
  cf-aig-custom-cost: {json}      (optional)
  cf-aig-cache-ttl: {seconds}     (optional)
  cf-aig-metadata: {json}        (optional)
Body:
  { model: "workers-ai/@cf/meta/llama-3.1-8b-instruct-fp8", messages: [...] }
```

- Uses the AI Gateway custom domain directly
- Service token headers (`CF-Access-Client-Id`/`CF-Access-Client-Secret`) authenticate the Worker through Cloudflare Access
- When a human user opens the UI in a browser, Access injects `cf.user_id` via the IdP session — no service token or API token needed in the browser
- Model names are prefixed with `workers-ai/`

### Gateway Settings API

Rate limiting is updated via PUT to the gateway (Guardrails has its own endpoint/PUT — see "Guardrails Toggle" below). **The live API requires `collect_logs`, `cache_invalidate_on_update`, and `cache_ttl`** — confirmed directly against the real API (2026-10-28): a request without them is rejected with `7001 Required`/`Expected number, received nan`. This isn't documented as a breaking change anywhere; it was just discovered by testing. The PUT endpoint also **replaces the gateway's config wholesale** — it does not partial-merge fields you omit (confirmed live: an earlier version of this handler silently flipped `authentication` from `true` to `false` by only sending rate-limiting fields, breaking Access-authenticated gateway-mode chat with a bare 401 — see the `authentication` field note on `GatewayConfig`). `settingsHandler` (via the shared `fetchCurrentGatewayConfig`/`baseGatewayPutBody` helpers) does a GET of the current gateway config first and spreads the _entire_ thing into the PUT body, then overrides only what it's intentionally changing:

```
GET /client/v4/accounts/{account_id}/ai-gateway/gateways/{gateway_name}   # read current config first
PUT /client/v4/accounts/{account_id}/ai-gateway/gateways/{gateway_name}
Body:
  {
    ...<everything from the GET, spread as-is>,
    cache_ttl: <preserved from GET, default 0>,
    collect_logs: <preserved from GET, default true>,
    cache_invalidate_on_update: <preserved from GET, default false>,
    rate_limiting_limit: 100, rate_limiting_interval: 60, rate_limiting_technique: "fixed",
  }
```

Spend limits are created via:

```
POST /client/v4/accounts/{account_id}/ai-gateway/gateways/{gateway_name}/spend-limits
Body:
  { budget: 1.0, window: "1d", dimensions: {} }
```

### Guardrails Toggle

Simple on/off (no per-category UI) via its own dedicated endpoint, `POST /api/guardrails` (`guardrailsHandler` in `src/index.ts`) — deliberately **not** folded into `/api/settings`'s rate-limit/spend-limit batch update, so flipping this one switch doesn't also silently re-apply whatever values happen to be sitting in that form. Takes effect immediately: the UI's checkbox `onchange` calls `toggleGuardrails()` directly, no separate "Apply" click needed. Admin-gated — see `requireAdmin`/`src/auth.ts`.

`guardrailsHandler` shares `fetchCurrentGatewayConfig(env)` and `baseGatewayPutBody(current)` with `settingsHandler` and `statsHandler` (GET current config, then spread it into the PUT body — same full-config-spread pattern described in Gateway Settings above, for the same reason: the PUT endpoint replaces the whole resource):

- **Enabling**: if the gateway already has a `guardrails` config (from the pre-fetch GET), re-sends it unchanged — never overwrites a previously fine-tuned hazard-category setup. If there's no existing config (first enable, or re-enabling after a disable), falls back to `DEFAULT_GUARDRAILS`: every category (`S1`-`S13`, `P1`) set to `FLAG` on both prompt and response — visible in logs, not silently blocking, safer for a live demo.
- **Disabling**: explicitly `delete`s the `guardrails` key from the PUT body (the spread alone would otherwise carry over an already-enabled config). Per Cloudflare's docs, omitting the key is what clears it server-side — there's no explicit `{enabled: false}` shape. This means a disable **discards** any hazard-category tuning; re-enabling later starts from `DEFAULT_GUARDRAILS`, not whatever was there before.
- `GET /api/stats` (`statsHandler`) exposes the gateway's actual current state as `guardrailsEnabled: boolean` (`isGuardrailsOn()` — true if `guardrails.prompt` or `guardrails.response` has any keys). The UI's `loadStats()` syncs both the checkbox and a top-of-page `#guardrailsBadge` (next to the gateway name, not buried in the Stats panel) to match on every load.

UI feedback details (tuned after user feedback that the first version felt sluggish and its confirmation flashed away): `toggleGuardrails()` shows activity instantly — the badge flips to "…" (yellow) and a persistent "Updating…" message appears — because the server roundtrip (GET + PUT against the Cloudflare API) takes 1-3s. It deliberately does **not** call `loadStats()` afterward (that resets every stat box to "…" and fires a second slow fetch, doubling the perceived latency); instead it updates the badge, the Stats-panel `statGuardrails` box, and the checkbox directly from the toggle response's `guardrailsEnabled`. The confirmation/error message under the checkbox is persistent (`show(..., timeoutMs=0)`) rather than the 5s auto-clear used elsewhere, since a transient message on a slow toggle read as "appeared then vanished". On failure the checkbox and badge revert immediately.

**Guardrails activity in chat output:** `chatHandler` enriches every successful `/api/chat` response with a `guardrails` field (`fetchGuardrailsActivity`, best-effort — a logs API failure never fails the chat). The gateway logs each Llama Guard evaluation as a **separate log entry** with `request_type: "llama-guard"`, model `@cf/meta/llama-guard-3-8b`, and its own `duration`/`tokens_in` — verified live (2026-10-28). There is no event-id response header to correlate with (checked — the response only carries `cf-aig-cache-status` etc.), so evaluations are matched by time window: entries with `request_type === "llama-guard"` and `created_at` within (request start − 2s clock-skew buffer). The response reports `{evaluations, totalMs, entries}` and the UI renders a `🛡 Guardrails: N Llama Guard evaluations (+X.Xs)` line under the OK line. The verdict fields (`score`, `guardrails`) in log entries stay **empty** for safe requests under FLAG-mode categories — they only populate on flagged/blocked content — so presence/latency of evaluations is the observable signal, not a "safe/unsafe" verdict.

**Gotcha — enabling Guardrails doesn't take effect instantly on the edge:** a chat request fired ~1s after the enable PUT still ran _without_ Guardrails (no llama-guard log entries, normal ~1.3s latency). The config change needs a couple of seconds to propagate before requests actually route through Llama Guard (verified: same request 2s+ later took 3.2s/8.1s with two llama-guard log entries each). If verifying, wait ~2-3s after enabling, then check for llama-guard entries in the logs — don't trust latency alone (it can be fast for other reasons) or absence alone.
**Gotcha — disabling is much slower to propagate than enabling (asymmetric):** verified live (2026-10-28, user-reported "guardrails fired every request despite checkbox"): chats fired up to **~26s after a successful disable PUT** still ran Llama Guard evaluations (the config already showed `guardrails: None`; a chat minutes later showed 0 evaluations). So enable takes ~2-3s to start applying, disable takes ~30-60s to stop applying. The UI now says this in the toggle confirmation and annotates 🛡 lines that appear while the checkbox is off ("edge is still applying the disable"). When a future report says "the toggle didn't work", check the request timeline against `modified_at` on the gateway config before assuming a code bug — a 🛡 line inside the propagation window after a disable is expected behavior, not a failure.

**Why this exists:** confirmed live that Guardrails — not model choice — is the dominant latency factor in this demo. Guardrails runs Llama Guard 3 8B as separate inference calls to evaluate the prompt and (separately) the response, on top of whatever chat model is selected. Measured directly against `ai-cost-demo`: a short request went from **~700ms with Guardrails off to 6-15+ seconds with it on** (8-20x), and that gap held across every model tested (1B through 8B) — Cloudflare's own docs estimate "~500ms per evaluation," and there are at least two evaluations per request (prompt + response), more for longer content that gets chunked. If a future report says the demo "is still slow" after already picking a small model, check Guardrails before anything else.

### Identity-Aware Gateway

1. Add a [custom domain](https://developers.cloudflare.com/ai-gateway/configuration/custom-domains/) to the AI Gateway
2. Create a [Cloudflare Access application](https://developers.cloudflare.com/cloudflare-one/policies/access/) for that domain
3. Create a service token and add a Service Auth policy at #1
4. Set `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET` as Worker secrets
5. Authenticate via SAML IdP (Okta, Entra, etc.) for human identity
6. AI Gateway automatically injects `cf.user_id` metadata on human requests
7. Service token requests get `cf.common_name` instead (visible in logs API, not dashboard)
8. Enables per-user spend limits, per-user rate limits, and User Insights behavioral baselines

### WARP Seamless Auth (Optional)

- Enable "Authenticate with Cloudflare One Client" on the Access application (not the policy)
- Requires WARP enrolled in the **same Zero Trust org** as the Access app
- Cross-org WARP enrollment does NOT work for seamless auth (policy allows the email, but WARP session must be from the same org)
- When working: browser goes straight to the UI — no OTP/IdP login page
- When not working: Access shows the OTP/IdP login page (still authenticates fine, just not seamless)
- To switch WARP org: `warp-cli registration new <team-name>` (replaces existing enrollment)

### Access Logout

- Logout button shown only in gateway mode (when `isGateway` is true server-side)
- Client-side: `fetch("/cdn-cgi/access/logout")` → wait 2s → redirect to `/demo`
- The 2s delay avoids a race condition where Access re-issues the cookie before the IdP session is fully invalidated
- The `/demo/logout` server-side route exists as a fallback but is not used by the button

## Known Limitations

- Spend limits are eventually consistent (burst can briefly exceed budget)
- Cost tracking is best-effort estimation based on token counts
- Max 20 spend limit rules per gateway
- Gateway stats endpoint may vary; adjust `/api/stats` if Cloudflare API changes
- Identity-Aware Gateway requires a custom domain and Cloudflare Access (not configurable through this Worker)
- WARP seamless auth requires same-org WARP enrollment; cross-org shows OTP page instead
- Access logout race condition: immediate re-login after logout can fail; 2s delay in the client-side logout handles this
- Requires Node.js 22+ (wrangler 4.x's own requirement) — CI runs on Node 22
- `wrangler.toml`/`wrangler.toml.example` ordering gotcha: `routes` must stay a top-level key, before any `[table]` header (`[observability]`, `[vars]`, `[[kv_namespaces]]`). TOML absorbs unbracketed keys into whichever table header precedes them — putting `[observability]` before `routes` silently drops the custom-domain routes on deploy with no error, only a warning (`Unexpected fields found in observability field: routes`). Hit and fixed this once already; keep `routes` first.
- Workers AI models get deprecated and removed (HTTP 410) without much notice — if traffic generation suddenly 410s, check the model against `GET /accounts/{id}/ai/models/search` before assuming the Worker/gateway/Access is broken
- See Security above for the admin-endpoint auth model and the accepted dev-tooling `npm audit` residual
- **"Caching isn't firing" has two independent causes, both verified live against `/api/chat` and the direct `/compat/chat/completions` gateway path — neither is a header/gateway-logic bug:**
  1. **Concurrency**: two requests fired at the same time (double-click before the first response returns, or **Send Burst**'s `Promise.all` over 5 requests) **always** both MISS — neither has a completed response yet to populate the cache. Fixed: `sendChat()` in `src/ui.ts` disables both Send buttons while a request is in flight; a blocked second click logs a warning instead of firing.
  2. **Propagation delay, even for genuinely sequential requests**: AI Gateway's cache write is not synchronous with the response it returns. Measured empirically (repeated trials, `/api/chat`): two identical requests fired the instant the first response returns HIT only ~2/5 (40%) of the time; spaced >=500ms apart, 5/5 (100%) across multiple trials. Mitigated, not eliminated: after a cache-enabled single Send completes, `sendChat()` holds the button disabled for an extra ~1s before allowing the next send, comfortably past the measured threshold. The hold message and the per-request output both now state that the FIRST send of any prompt is always a MISS by definition (that response populates the cache) and a resend of the same prompt shows the HIT — after a user report read first-send MISSes as "caching is broken" even though their own logs showed every repeated send within ~1.5s hitting.
  - If a future report says caching doesn't work: reproduce with the actual UI (which now has both mitigations) before assuming the gateway/header logic is broken. If testing via raw curl, insert a `sleep 0.5` (or more) between the two requests, or expect occasional MISS,MISS at 0 delay — that's expected AI Gateway cache behavior, not a regression.
